# AgentOps — Relationships and End-to-End Testing Guide

This document is the reference for the database relationships and for verifying the app from a clean state. It is written so a group member or marker can reproduce the full CRUD workflow without knowing the implementation first.

---

## 1. System overview

```text
Browser
  ↓ REST API
Node.js + Express
  ↓ parameterised SQL
MySQL (agentops)
  ↓
Mock agent or optional Live AI provider
```

The browser never connects to MySQL directly. The backend is the only component with database credentials. Before a run, the backend reads the approved artifacts of the task's prerequisites from MySQL and passes them to the agent as input. Agent outputs are returned to the backend, validated, and then written to MySQL.

Default mode is `MOCK`: no API key, network, or paid service is required. Live mode is optional.

## 2. Table inventory

| Table | Primary key | Foreign keys | Main purpose |
|---|---|---|---|
| `users` | `user_id` | None | Human users and reviewers |
| `projects` | `project_id` | `owner_id → users.user_id` | Software-project workspaces |
| `agents` | `agent_id` | None | Planner, coder, tester and reviewer agents |
| `tasks` | `task_id` | `project_id → projects.project_id`, `created_by → users.user_id` | Current task state and requirements |
| `task_dependencies` | `(task_id, depends_on_task_id)` | Both columns → `tasks.task_id` | Relationship table: recursive M:N relationship on tasks (dependency graph) |
| `task_assignments` | `(task_id, agent_id, assignment_role)` | `task_id → tasks.task_id`, `agent_id → agents.agent_id` | Relationship table: M:N relationship between tasks and agents (which agents participate in a task); unique key `uk_one_primary_per_task` allows at most one `PRIMARY` agent per task |
| `agent_runs` | `agent_run_id` | `task_id → tasks.task_id`, `agent_id → agents.agent_id` | Execution history and status |
| `artifacts` | `artifact_id` | `agent_run_id → agent_runs.agent_run_id` | Files or Markdown generated by an agent run; the owning task is derived through `agent_runs` |
| `reviews` | `review_id` | `artifact_id → artifacts.artifact_id`, `reviewer_id → users.user_id` | Human review decisions |
| `run_inputs` | `(agent_run_id, artifact_id)` | `agent_run_id → agent_runs.agent_run_id`, `artifact_id → artifacts.artifact_id` | Relationship table: M:N "uses" relationship between agent runs and artifacts (which approved upstream artifacts a run received as input) |

Agent recommendations, risk scores and duplicate-task warnings are computed on demand and returned only in the API response; they are not stored in any table.

## 3. Complete relationship table

| Parent table | Child table | Relationship | FK column in child | Referenced column | Cardinality | Delete rule | Meaning |
|---|---|---|---|---|---|---|---|
| `users` | `projects` | User owns projects | `projects.owner_id` | `users.user_id` | 1 user : 0..N projects | `RESTRICT` | A project must have a valid owner |
| `users` | `tasks` | User creates tasks | `tasks.created_by` | `users.user_id` | 1 user : 0..N tasks | `RESTRICT` | A task keeps its creator reference |
| `users` | `reviews` | User writes reviews | `reviews.reviewer_id` | `users.user_id` | 1 user : 0..N reviews | `RESTRICT` | Review decisions remain attributable |
| `projects` | `tasks` | Project contains tasks | `tasks.project_id` | `projects.project_id` | 1 project : 0..N tasks | `CASCADE` | Deleting a project removes its tasks |
| `tasks` | `task_dependencies` | Task has dependencies | `task_dependencies.task_id` | `tasks.task_id` | 1 task : 0..N dependency rows | `CASCADE` | Deleting a task removes outgoing dependencies |
| `tasks` | `task_dependencies` | Task blocks other tasks | `task_dependencies.depends_on_task_id` | `tasks.task_id` | 1 task : 0..N dependency rows | `CASCADE` | Deleting a task removes incoming dependencies |
| `tasks` | `task_assignments` | Task is assigned to agents | `task_assignments.task_id` | `tasks.task_id` | 1 task : 0..N assignments | `CASCADE` | One task can involve multiple agents, at most one of them as `PRIMARY` |
| `agents` | `task_assignments` | Agent receives assignments | `task_assignments.agent_id` | `agents.agent_id` | 1 agent : 0..N assignments | `RESTRICT` | An agent with assignments cannot be silently deleted |
| `tasks` | `agent_runs` | Task has execution history | `agent_runs.task_id` | `tasks.task_id` | 1 task : 0..N runs | `CASCADE` | Deleting a task removes its run history |
| `agents` | `agent_runs` | Agent performs runs | `agent_runs.agent_id` | `agents.agent_id` | 1 agent : 0..N runs | `RESTRICT` | Historical runs keep a valid agent reference |
| `agent_runs` | `artifacts` | Run produces artifacts | `artifacts.agent_run_id` | `agent_runs.agent_run_id` | 1 run : 0..N artifacts | `CASCADE` | An artifact always belongs to a run; its task is the run's task (`agent_runs.task_id`) |
| `artifacts` | `reviews` | Artifact receives reviews | `reviews.artifact_id` | `artifacts.artifact_id` | 1 artifact : 0..N reviews | `CASCADE` | Deleting an artifact removes its reviews |
| `agent_runs` | `run_inputs` | Run uses input artifacts | `run_inputs.agent_run_id` | `agent_runs.agent_run_id` | 1 run : 0..N input rows | `CASCADE` | Deleting a run removes the record of what it used |
| `artifacts` | `run_inputs` | Artifact is used as input | `run_inputs.artifact_id` | `artifacts.artifact_id` | 1 artifact : 0..N input rows | `CASCADE` | Deleting an artifact removes the records of the runs that used it |

Together, the last two rows implement the M:N relationship "a run uses artifacts". There is no direct tasks → artifacts relationship: deleting a task removes its runs, which removes their artifacts, their reviews and their `run_inputs` rows.

### 3.1 Table details

#### `users`

```text
users(
  user_id PK,
  username UNIQUE,
  email UNIQUE,
  password_hash,
  role,
  created_at
)
```

Stores human accounts. Used by projects (`owner_id`), tasks (`created_by`), and human reviews (`reviewer_id`).

#### `projects`

```text
projects(
  project_id PK,
  owner_id FK → users.user_id,
  name,
  description,
  status,
  created_at
)
```

One project can contain many tasks. A project has one owner in this MVP.

#### `agents`

```text
agents(
  agent_id PK,
  name UNIQUE,
  role,
  provider,
  model_name,
  execution_mode,
  status,
  created_at
)
```

The four specialist roles are `PLANNER`, `CODER`, `TESTER`, and `REVIEWER`.

#### `tasks`

```text
tasks(
  task_id PK,
  project_id FK → projects.project_id,
  created_by FK → users.user_id,
  title,
  description,
  required_role,
  status,
  priority,
  estimated_hours,
  created_at,
  updated_at
)
```

`tasks.status` stores the current state. Historical execution details belong in `agent_runs`.

Valid statuses:

```text
TODO, IN_PROGRESS, BLOCKED, REVIEW, DONE, CANCELLED
```

Status changes follow the workflow:

```text
Manual (PATCH /api/tasks/:taskId or the Edit dialog):
  TODO → BLOCKED, TODO → CANCELLED
  BLOCKED → TODO, BLOCKED → CANCELLED
  CANCELLED → TODO

Workflow only:
  TODO / BLOCKED / REVIEW → IN_PROGRESS   (an agent run starts)
  IN_PROGRESS → REVIEW                    (run succeeds; DONE for a reviewer agent)
  IN_PROGRESS → BLOCKED                   (run fails)
  REVIEW → DONE                           (human approves the unreviewed artifact)
```

Any other manual change is rejected with `409 INVALID_STATUS_TRANSITION`.

#### `task_dependencies`

```text
task_dependencies(
  task_id PK/FK → tasks.task_id,
  depends_on_task_id PK/FK → tasks.task_id
)
```

This is a relationship table, not an entity: it implements the recursive M:N relationship on tasks (a self-referencing many-to-many relationship). It represents:

```text
task A depends on task B
```

The composite primary key prevents duplicate dependency rows. A check constraint prevents a task from depending on itself.

#### `task_assignments`

```text
task_assignments(
  task_id PK/FK → tasks.task_id,
  agent_id PK/FK → agents.agent_id,
  assignment_role PK,
  assigned_at,
  UNIQUE uk_one_primary_per_task ((CASE WHEN assignment_role = 'PRIMARY' THEN task_id END))
)
```

This is a relationship table, not an entity: it implements the M:N relationship between tasks and agents with descriptive attributes `assignment_role` and `assigned_at`. There is no surrogate key; the composite primary key `(task_id, agent_id, assignment_role)` allows a task to involve multiple agents, for example a PRIMARY coder and a SUPPORT tester, while preventing the same agent from holding the same role on a task twice. A secondary index on `agent_id` supports lookups from the agent side.

The functional unique key `uk_one_primary_per_task` allows at most one `PRIMARY` agent per task: for a `PRIMARY` row the indexed expression is the `task_id`, for any other role it is `NULL`, and a unique index ignores `NULL`s. When a task is re-run by a different agent, the orchestrator deletes the old `PRIMARY` row and inserts one for the new agent in the same transaction, so the `PRIMARY` role moves to the agent that ran the task last.

#### `agent_runs`

```text
agent_runs(
  agent_run_id PK,
  task_id FK → tasks.task_id,
  agent_id FK → agents.agent_id,
  status,
  started_at,
  finished_at,
  latency_ms,
  input_summary,
  output_summary,
  raw_output,
  error_message,
  model_name,
  created_at
)
```

This is the execution history. A successful run is later connected to one or more artifacts, and to the input artifacts it used through `run_inputs`.

A run is started in one transaction: the task is claimed with a conditional `UPDATE tasks SET status = 'IN_PROGRESS' WHERE task_id = ? AND status IN ('TODO', 'BLOCKED', 'REVIEW')`, an agent is claimed with `UPDATE agents SET status = 'BUSY' WHERE agent_id = ? AND status = 'AVAILABLE'`, and the `RUNNING` `agent_runs` row and its `run_inputs` rows are inserted. If the task update affects no row, another run already started (`409 TASK_RUNNING`); if no agent can be claimed, the whole transaction is rolled back, including the task status (`409 NO_AGENT`). If the agent then fails, one transaction sets the run to `FAILED`, the agent back to `AVAILABLE` and the task to `BLOCKED` (`502 AGENT_FAILED`).

#### `artifacts`

```text
artifacts(
  artifact_id PK,
  agent_run_id FK → agent_runs.agent_run_id,
  artifact_type,
  file_name,
  file_path,
  content,
  created_at
)
```

Artifacts keep the actual generated Markdown/code text in `content`, so the UI can display it without an external file service.

An artifact has no `task_id` column. Its task is derived through the run that produced it:

```sql
SELECT ar.artifact_id, ar.file_name, r.task_id
FROM artifacts ar
JOIN agent_runs r ON r.agent_run_id = ar.agent_run_id;
```

Storing the task again on `artifacts` would be redundant and could disagree with the run.

#### `reviews`

```text
reviews(
  review_id PK,
  artifact_id FK → artifacts.artifact_id,
  reviewer_id FK → users.user_id,
  status,
  comment,
  created_at,
  reviewed_at
)
```

The human decision is kept separately from the AI output. This supports the human-in-the-loop workflow.

`POST /api/tasks/:taskId/approve` only works on a task in `REVIEW` (`409 TASK_NOT_IN_REVIEW` otherwise) that has an unreviewed artifact from a successful run (`409 NO_ARTIFACT_TO_REVIEW` otherwise). It inserts an `ACCEPTED` review for the newest such artifact, sets the task to `DONE`, and returns `{ task, reviewId, artifact: { artifactId, fileName } }`.

#### `run_inputs`

```text
run_inputs(
  agent_run_id PK/FK → agent_runs.agent_run_id,
  artifact_id PK/FK → artifacts.artifact_id
)
```

This is a relationship table, not an entity: it implements the M:N "uses" relationship between agent runs and artifacts. One run can use several artifacts, and one artifact can be used by several runs. The composite primary key prevents recording the same input twice for a run, and a secondary index on `artifact_id` supports the reverse lookup ("which runs used this artifact?"). Both foreign keys use `ON DELETE CASCADE`.

When a task runs, the orchestrator (`getApprovedInputs` in `src/orchestrator.js`) selects, for each direct prerequisite task, its latest artifact that has an `ACCEPTED` review (using `ROW_NUMBER() OVER (PARTITION BY dep.task_id ORDER BY ar.created_at DESC, ar.artifact_id DESC)`). These artifacts are passed to the agent, and one `run_inputs` row is inserted per artifact in the same transaction that creates the run. Seed data: run 2 (`Design database schema`) used artifact 1 (`requirements.md`).

The Mermaid ER diagram is in:

It includes the `uses` relationship between agent runs and artifacts (`run_inputs`) and has no direct tasks — artifacts relationship.

tasks → agent_runs → artifacts → reviews

Some test cases (BLOCK-01, RULE-01, CONC-01) call the API directly with `curl`. Sign in once and keep the session cookie:

```bash

  -H 'Content-Type: application/json' \

  http://localhost:3000/api/auth/login

```text
{"user":{"user_id":1,"username":"alice","email":"alice@example.com","role":"ADMIN"}}

Later requests pass `-b /tmp/agentops-cookies.txt`. Errors are returned as `{"error":{"message":...,"code":...,"details":...}}`.

### CONC-01 — Concurrent runs cannot double-start a task

This test uses the seeded task `Write README and setup guide` (task `6`, role `PLANNER`, its only dependency is done) and the API session from 5.4.

**Steps**

1. Send two run requests for the same task at the same moment:

```bash
for i in 1 2; do
  curl -s -o /tmp/agentops-run-$i.json -w "request $i: HTTP %{http_code}\n" \
    -b /tmp/agentops-cookies.txt -H 'Content-Type: application/json' -d '{}' \
    http://localhost:3000/api/tasks/6/run &
done
wait
grep -ho '"code":"[A-Z_]*"' /tmp/agentops-run-*.json
```

2. Click **Refresh** in the UI.

**Expected result**

- One request prints `HTTP 201` and the other `HTTP 409`, in either order.
- The `grep` prints `"code":"TASK_RUNNING"`.
- `Write README and setup guide` is in `REVIEW` with exactly one new run by `Planner Agent`, and `Planner Agent` is `AVAILABLE` again.

Whichever request claims the task first sets it to `IN_PROGRESS` with the conditional `UPDATE tasks SET status = 'IN_PROGRESS' ... WHERE status IN ('TODO', 'BLOCKED', 'REVIEW')`. The other request either already sees `IN_PROGRESS`, or its own conditional `UPDATE` waits for the first transaction's row lock, re-reads the committed status and matches no row. Either way it is rejected with `TASK_RUNNING` before it books an agent or inserts a run. The default mock delay (250 ms) is long enough for two requests sent together; to widen the window, start the server with `MOCK_DELAY_MS=2000 npm start`. Requests sent one after the other both succeed, because a task in `REVIEW` may be re-run.

**SQL check**

```sql
SELECT
  r.agent_run_id,
  r.status AS run_status,
  a.name AS agent,
  t.status AS task_status,
  (SELECT COUNT(*) FROM run_inputs ri WHERE ri.agent_run_id = r.agent_run_id) AS inputs
FROM agent_runs r
JOIN agents a ON a.agent_id = r.agent_id
JOIN tasks t ON t.task_id = r.task_id
WHERE r.task_id = 6;
```

Expected: exactly one row: `SUCCESS`, `Planner Agent`, `REVIEW`, `1` input (`requirements.md`). The rejected request left no run and no `run_inputs` row.

```sql
SELECT
  (SELECT COUNT(*) FROM agents WHERE status = 'BUSY') AS busy_agents,
  (SELECT COUNT(*) FROM tasks WHERE status = 'IN_PROGRESS') AS in_progress_tasks,
  (SELECT COUNT(*) FROM agent_runs WHERE status = 'RUNNING') AS running_runs;
```

Expected: `0`, `0`, `0`.

### RULE-01 — Status cannot skip the workflow

`IN_PROGRESS`, `REVIEW` and `DONE` can only be reached by running an agent and approving its artifact. This test uses the seeded task `Review login implementation` (task `5`, status `TODO`, no runs) and the API session from 5.4.

**Steps**

1. Try to mark the task done directly:

```bash
curl -s -w '\nHTTP %{http_code}\n' -b /tmp/agentops-cookies.txt \
  -X PATCH -H 'Content-Type: application/json' -d '{"status":"DONE"}' \
  http://localhost:3000/api/tasks/5
```

2. Put the task into `REVIEW` without running an agent (setup only):

```sql
UPDATE tasks SET status = 'REVIEW' WHERE task_id = 5;
```

3. Try to approve it:

```bash
curl -s -w '\nHTTP %{http_code}\n' -b /tmp/agentops-cookies.txt \
  -H 'Content-Type: application/json' -d '{}' \
  http://localhost:3000/api/tasks/5/approve
```

4. Reset the task:

```sql
UPDATE tasks SET status = 'TODO' WHERE task_id = 5;
```

**Expected result**

- Step 1 returns `HTTP 409` with code `INVALID_STATUS_TRANSITION`, the message `Cannot change status from TODO to DONE directly. IN_PROGRESS, REVIEW and DONE are set by running an agent and approving its artifact.`, and `details` `{"from":"TODO","allowed":["BLOCKED","CANCELLED"]}`.
- Step 3 returns `HTTP 409` with code `NO_ARTIFACT_TO_REVIEW` and the message `There is no unreviewed artifact for this task. Run an agent before approving.`
- Approving a task that is not in `REVIEW` (for example task `5` after step 4) returns `HTTP 409` with code `TASK_NOT_IN_REVIEW`.
- In the UI, the **Edit** dialog does not offer `REVIEW` or `DONE`, and the **Approve** button only appears on `REVIEW` tasks. Between steps 2 and 4 you can click **Refresh** and then **Approve** on `Review login implementation` instead of step 3; the toast shows the same `NO_ARTIFACT_TO_REVIEW` message.

**SQL check**

```sql
SELECT t.task_id, t.status, COUNT(rev.review_id) AS reviews
FROM tasks t
LEFT JOIN agent_runs r ON r.task_id = t.task_id
LEFT JOIN artifacts ar ON ar.agent_run_id = r.agent_run_id
LEFT JOIN reviews rev ON rev.artifact_id = ar.artifact_id
WHERE t.task_id = 5
GROUP BY t.task_id, t.status;
```

Expected after step 4: status `TODO` and `0` reviews; neither rejected request changed the database.

INSERT INTO task_assignments (task_id, agent_id, assignment_role)

### SQL-01 — Relationship integrity queries

Run the following queries and confirm that no relationship is broken.

#### Tasks with their projects and creators

```sql
SELECT
  t.task_id,
  t.title,
  p.name AS project,
  u.username AS creator
FROM tasks t
JOIN projects p ON p.project_id = t.project_id
JOIN users u ON u.user_id = t.created_by
ORDER BY t.task_id;
```

#### Tasks with their assigned agents

```sql
SELECT
  t.task_id,
  t.title,
  ta.assignment_role,
  a.name AS agent,
  a.role
FROM tasks t
LEFT JOIN task_assignments ta ON ta.task_id = t.task_id
LEFT JOIN agents a ON a.agent_id = ta.agent_id
ORDER BY t.task_id, ta.assignment_role;
```

#### Full run and review trace

```sql
SELECT
  t.title AS task,
  a.name AS agent,
  r.status AS run_status,
  ar.file_name,
  rev.status AS review_status
FROM tasks t
LEFT JOIN agent_runs r ON r.task_id = t.task_id
LEFT JOIN agents a ON a.agent_id = r.agent_id
LEFT JOIN artifacts ar ON ar.agent_run_id = r.agent_run_id
LEFT JOIN reviews rev ON rev.artifact_id = ar.artifact_id
ORDER BY t.task_id, r.agent_run_id, ar.artifact_id;
```

#### Artifacts with their task (derived through the run)

```sql
SELECT
  ar.artifact_id,
  ar.file_name,
  r.agent_run_id,
  t.task_id,
  t.title AS task
FROM artifacts ar
JOIN agent_runs r ON r.agent_run_id = ar.agent_run_id
JOIN tasks t ON t.task_id = r.task_id
ORDER BY ar.artifact_id;
```

Expected on seed data: `requirements.md` belongs to task `1` and `schema.sql` to task `2`.

#### Run inputs come from direct prerequisites

```sql
SELECT ri.agent_run_id, ri.artifact_id
FROM run_inputs ri
JOIN agent_runs r ON r.agent_run_id = ri.agent_run_id
JOIN artifacts ia ON ia.artifact_id = ri.artifact_id
JOIN agent_runs src ON src.agent_run_id = ia.agent_run_id
LEFT JOIN task_dependencies td
  ON td.task_id = r.task_id AND td.depends_on_task_id = src.task_id
WHERE td.task_id IS NULL;
```

Expected: no rows. Every input artifact was produced by a task that the run's task directly depends on.

#### Duplicate dependency check

```sql
SELECT task_id, depends_on_task_id, COUNT(*) AS occurrences
FROM task_dependencies
GROUP BY task_id, depends_on_task_id
HAVING COUNT(*) > 1;
```

Expected: no rows, because the composite primary key prevents duplicates.

#### Self-dependency check

```sql
SELECT *
FROM task_dependencies
WHERE task_id = depends_on_task_id;

## 10. Troubleshooting

### `ECONNREFUSED`

MySQL is not running:

```bash
brew services start mysql
mysqladmin ping
```

### `ER_ACCESS_DENIED_ERROR`

Update the database credentials in `.env`:

```env
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=root
DB_PASSWORD=your_password
DB_NAME=agentops
```

### `EADDRINUSE`

Port 3000 is already in use. Stop the old server or change:

```env
PORT=3001
```

Then open `http://localhost:3001`.

### Login fails after a database reset

Use the seeded account:

```text
alice@example.com
password123
```

If needed, rerun:

```bash
npm run db:setup
```

### Blank page

Check the server terminal for errors, then verify:

```bash
curl http://localhost:3000
```

If the server responds, reload the browser and check the browser console.
